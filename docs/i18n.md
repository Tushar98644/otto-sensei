# Languages (i18n)

Plan for serving Otto in Spanish (`es`), Portuguese–Brazil (`pt-BR`), French (`fr`) and German (`de`). English stays the default. Decided 2026-11-25: translate everything — website, app, resume engine, emails and jobs — one shippable phase at a time, with English output unchanged at every step.

## Decisions

| Question      | Decision                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| URL shape     | English unprefixed (URLs never change). Others prefixed: `/es`, `/pt-br`, `/fr`, `/de`. `/en/*` 308s to the unprefixed path.                                                                                                                                                                                                                                                                 |
| Slugs         | English slugs under the prefix (`/es/resume-builder`).                                                                                                                                                                                                                                                                                                                                       |
| Routing       | Every page under `src/app/[lang]/`, root layout `src/app/[lang]/layout.tsx` with `<html lang>` from `next/root-params`. The proxy rewrites unprefixed paths to `/en/…`. Outside `[lang]`: `api/`, `auth/`, metadata routes (`sitemap`, `robots`, `llms*`, OG image, icons) and `p/` (own root layout, the portfolio's language).                                                             |
| App language  | Not in the URL. `user_settings.locale`, mirrored to an `otto_lang` cookie; the proxy rewrites app paths (`/dashboard`, `/studio`, `/account`, `/reminder`, `/s`, `/extension`) to that locale. `/{locale}/<app path>` sets the cookie and 307s to the unprefixed path. No Accept-Language redirects.                                                                                         |
| Library       | Small typed layer of our own, no dependency. English messages `as const` are the source of truth; other locales `satisfies Translation<typeof en>`, so a missing key fails `tsc`. `{var}` interpolation, plural objects via `Intl.PluralRules`, `<b>`/`<link>` rich-text tags. next-intl (4.16, supports Next 16) is the fallback; keep a similar API (`getMessages`, `useMessages`, `fmt`). |
| Client cost   | Marketing pages get no provider: client islands receive translated strings as props. App layouts pass only their namespaces to a client provider, with a byte budget test.                                                                                                                                                                                                                   |
| Language axes | UI locale, resume language (`lang` in the resume JSON, detected, user can override) and job-post language are separate.                                                                                                                                                                                                                                                                      |
| AI prompts    | System prompts stay English and byte-stable for the cache; the language goes in the user message (`<languages resume ui post/>`).                                                                                                                                                                                                                                                            |
| Translation   | AI translation with a glossary, neutral Latin American Spanish, informal address (tú, você, tu, du); native review of top pages before heavy promotion.                                                                                                                                                                                                                                      |
| Publishing    | Per locale and per page; the language setting in the app stays hidden until the whole app is translated.                                                                                                                                                                                                                                                                                     |

## Phases

Each phase ships to main on its own and leaves English byte-identical.

| Phase               | What                                                                                                                                                                                                                           | Size      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------- |

| P1 Content language | Detector, resume `lang`, lint language packs (neutral checks only for non-English until packs land), import-parser tables, AI language tags and guards, moderation lists, PDF/DOCX labels                                      | L         |

| P3 App              | Extract dashboard, studio, portfolio, account, API errors, `Intl` cleanup; translations; then show the language setting                                                                                                        | XL        |

| P7 Extension        | Otto for Chrome's words through `chrome.i18n`, store listings per language                                                                                                                                                     | S–M       |

## How it works (P0, as built)

**Locales** (`src/i18n/config.ts`): `LOCALES` lists all five; `ENABLED_LOCALES` is the switch that routes and prerenders one (all five since P2; pages are published per locale, see P2 below). Each locale has a URL segment (`pt-BR` → `pt-br`), an `Intl` tag (`en` → `en-US`, so English numbers and dates don't change; `es` → `es-419`) and an Open Graph locale. `matchLocale()` maps any BCP-47 tag to ours (`es-MX` → `es`, `pt-PT` → `pt-BR`).

**Routes.** Every page is under `src/app/[lang]/`. The root layout `src/app/[lang]/layout.tsx` sets `<html lang>` (from the segment; `getMessages` reads it through `next/root-params`), returns only enabled locales from `generateStaticParams` and 404s any other segment. Its `generateMetadata` passes `src/app/opengraph-image.tsx` on by hand: that file sits above the layout now, and a layout's `openGraph` would otherwise replace its image. Portfolios have their own root layout, `src/app/p/[slug]/layout.tsx` (in the portfolio's language, see Public portfolios), and both share `src/components/site/root-document.tsx`. Outside `[lang]`: `api/`, `auth/`, `p/`, `sitemap.ts`, `robots.ts`, `llms.txt`, `llms-full.txt`, `opengraph-image`, `icon.svg`, `apple-icon`, `global-not-found.tsx` and `global-error.tsx` (Next needs it at the app root; the layout and its messages are what broke, so it carries a small map of its own words in five languages and picks one from a readable `otto_lang` cookie or the broken page's `<html lang>`, else English).

**404.** A URL no route matches gets `src/app/global-not-found.tsx` (`experimental.globalNotFound`): a static page that draws the old 404 in its own English document, since a root layout under `[lang]` can't hold the app-wide one. A `[lang]/[...rest]` catch-all calling `notFound()` was tried and dropped: under a root layout with a dynamic segment, Next answers it with an empty error shell (status 404, the page drawn only in the browser), checked on a production build. `notFound()` inside a page still renders the nearest `not-found.tsx` (`src/app/[lang]/not-found.tsx`), as before. Since P2 that `not-found.tsx` is localized; a localized 404 for unmatched URLs would need global-not-found reading a locale header the proxy sets (it would turn dynamic), or a Next release that renders the catch-all on the server. Paths the proxy never sees (`/api/…`, `/p/a/b`, missing files) can still reach `[lang]` with a segment that isn't a locale; the root layout answers those with a bare 404.

**Proxy** (`src/proxy.ts`, rules in `src/i18n/routing.ts`). Locale first; then the sign-in redirects, session refresh and `/login` variants run unchanged on the visible path without its prefix; then a rewrite to `/{segment}{path}`:

- `/en` and `/en/*`: 308 to the unprefixed path.
- `/{live locale}/{app path}`: sets `otto_lang` and 307s to the unprefixed app path (`/en/dashboard` is the way back to English).
- `/{live locale other than en}/{public path}`: served as is.
- App paths (`/dashboard`, `/studio`, `/account`, `/reminder`, `/s`, `/extension`): `/{otto_lang if live, else en}/…`.
- Everything else: `/en/…`. A prefix that isn't live is an unknown path (`/es/pricing` → `/en/es/pricing` → 404), and its cookie is never set.
- Untouched: `api/`, `auth/`, `p/`, `_next/`, the folders and files of `public/`, and the root metadata routes. `src/i18n/routing.test.ts` walks `public/` and `src/app/` so a new folder can't be hidden.

**Messages** (`src/i18n/messages/`). `en/<namespace>.ts` (`as const`) is the source of truth, listed in `en/index.ts`. Another locale adds `<locale>/<namespace>.ts` (`satisfies Translation<Messages["<namespace>"]>`) and one line in its `index.ts`; a namespace it hasn't translated reads in English. A file's name is its namespace in kebab case (`job-match.ts` holds `jobMatch`, `match-reasons.ts` holds `matchReasons`). Namespaces, all translated in the four languages: `common`, `site`, `home`, `pricing`, `product`, `jobMatch` (the /job-match page), `matchCheck`, `legal`, `login` (P2); `seo`, `compare`, `ats`, `resumeExamples`, `resumeTemplates` (P5); `dashboard`, `jobs`, `applications`, `letters`, `interview`, `prep`, `email`, `app`, `studio`, `studioEditor`, `studioSections`, `studioTailor`, `studioDownload`, `jobForm`, `onboarding`, `accountMenu`, `portfolio`, `portfolioContent`, `portfolioDesigns`, `account`, `share`, `api` (P3); `signIn`, `upgrade`, `otto`, `shareLinks`, `formats`, `ui`, `calendar`, `github` (P3 leftover sweep); `matchReasons`, `jobsShared` (P6); `emails` (P4); `lint` (P1: the resume checks' messages, help and review). `portfolioDesigns` keeps one file per design in `<locale>/portfolio-designs/`, gathered by `portfolio-designs.ts`.

**Reading them.** Server Components (and `generateMetadata`) call `getMessages(ns)`, `getLocale()` and `getFormat()` from `src/i18n/server.tsx`, which read the `[lang]` root param; route handlers and server actions can't (Next doesn't allow root params there), so they take the locale from the cookie or the account. Client components below `<MessagesFor namespaces={[…]}>` call `useMessages(ns)`, `useLocale()` and `useFormat()` from `src/i18n/client.tsx`; only the named namespaces reach the browser. Helpers: `fmt()` fills `{name}` (the English template types its values), `formatFor(locale).plural(forms, count)` picks a form with `Intl.PluralRules`, `rich()` turns `<b>` and `<link>` into elements, and `formatFor(locale)` keeps one `Intl` formatter per locale and options.

**Checks.** `src/i18n/messages.test.ts` runs `checkMessages` (`src/i18n/check.ts`: keys, placeholders and tags match English, each language's plural forms, no empty or still-English text) over every locale file (a template of placeholders alone, like `{count} {label}`, never counts as still in English; `SAME_AS_ENGLISH` lists the real words spelled alike), and checks that a locale publishes a page exactly when every namespace it reads is translated, and that the marketing core is published. Vitest stubs `next/root-params` with `src/i18n/testing.ts`.

**Dashboard (P3).** `src/app/[lang]/dashboard/layout.tsx` wraps the shell in `<MessagesFor namespaces={DASHBOARD_NAMESPACES}>` (`app`, `dashboard`, `jobs`, `applications`, `interview`, `letters`). A page whose parts need more sends them in its own `MessagesFor` (`PAGE_NAMESPACES` in `namespaces.ts`: `prep` on the Interview prep pages, `email` on Applications); a nested provider adds its namespaces to the layout's, so they stay out of every other page's payload. `namespaces.test.ts` keeps the layout's payload, and the layout's plus each page's, under 110 KB (the sweep raised it from 90 KB; see Leftover sweep for today's sizes). Page titles come from `page-title.ts`. Client components read `useMessages(ns)` and `useFormat()`; pure helpers take the messages and `Format` as arguments, with English defaults where the studio or a test still calls them bare, and tests pass the English ones from `src/components/dashboard/messages-testing.tsx` (`inEnglish`, `inLocale`). Parts the studio or a page without a provider also draw read `useMessagesOr(ns, english)` (`OttoWorking`, `ProMark`, the try-Pro label) or take their words as props or arguments with English defaults (`status-menu`, `guide-video`, `copyText`, `undoToast`, `trashWithUndo`, `timeAgo`, `errorMessage`). A word that reads the same in a language (German "Jobs", French "Portfolio") goes in `SAME_AS_ENGLISH` in `messages.test.ts`.

**API errors (P3).** Routes keep writing their errors in English. Each user-facing handler is exported through `withApiLocale` (`src/lib/api/localize.ts`): when `otto_lang` names a live locale other than English, a JSON error answer's `message` is looked up by its English text in the `api` namespace, whole or a run of sentences at a time, templates carrying `{values}` over (numbers, waits like "2 minutes" and days like "Dec 1" are re-worded for the reader), and the answer keeps its status, code and headers. English answers pass through untouched, and so does any message without a translation. `localize.test.ts` checks every error sentence in the wrapped routes has a translation in each language, so a new one fails the suite until it is added. Cron, inbound email, the Chrome extension's routes, the billing webhook, health and the calendar feed aren't wrapped.

**Portfolio, Account and share pages (P3).** A `MessagesProvider` inside another adds its namespaces to the outer one's (same locale only), so a page sends just what it adds. The portfolio editor (`/dashboard/portfolio`) adds `portfolio` and `portfolioContent` (about 21 KB in English, 24 KB in French and German); `/account` and `/dashboard/account` add `account` (about 18 KB, 21 KB); `/s` sends `share` (about 2 KB). Each has a `namespaces.test.ts` budget. The extension connect and reminder pages have no provider: their server pages pass `account.extension.connect` and `account.reminder` as props, with the locale. Store functions that toast outside React take their words as an argument (`savePortfolio(patch, words)`); the content autosave gets them from `useContentSaveWords`. Prices stay USD, written the reader's way (`components/account/local-prices.ts`; in English they match `lib/billing/prices`). The delete-account confirm word is translated (ELIMINAR, EXCLUIR, SUPPRIMER, LÖSCHEN). Tests render with `withMessages(locale, namespaces, node)` from `src/i18n/messages-testing.tsx`.

**Public portfolios.** `/p/[slug]` reads the language set on the owner's resume (`PublicPortfolio.lang`, from the snapshot): `<html lang>`, the Open Graph locale, the title and description fallbacks and the share image's label follow it; a page with none set, or a missing page, stays English. The owner's own words are never translated.

**Portfolio designs.** Each of the 15 designs draws its own words (section labels, buttons, empty states, Gazette's newspaper lines, Retro's desktop, Terminal's help) from `portfolioDesigns.<design>`, in the portfolio's language (`designLocale(view)` in `templates/parts.tsx`: the resume's `lang`), never the visitor's. Templates take them as a `words` prop: `/p/[slug]` loads them on the server for `portfolioLocale()` (no client provider, caching unchanged), and the editor's `LazyTemplate` loads the language's file (`loadDesignWords`, one chunk per language shared by every design) alongside the design's code; `preloadTemplate(id, lang)` warms both. Client islands get only the strings they show, plus the locale when they format dates or numbers. Dates and numbers go through `designFormat(view)` or `formatFor(locale)`. `templates/english.test.tsx` draws every design in four states against `golden/english.json`, hashed from the code before the extraction (React's empty `<!-- -->` separators aside); `spanish.test.tsx` draws Navy, Gazette and the editor preview in Spanish. A few English counts keep their old wording ("1 stars", "1 weeks"), noted in the English files.

**App language.** `user_settings.locale` (null: never chosen; a check allows the five codes) and `PUT /api/language` with `{ "locale": "en" }` (signed in, same-site JSON, 30 changes an hour) save it and set `otto_lang` (httpOnly, a year). Only live locales are accepted, and the app doesn't offer the choice yet.

**Golden HTML.** Build `main`, `bun scripts/golden-html.ts save <folder>`; build your change, `bun scripts/golden-html.ts compare <folder>`. It compares every prerendered English page after taking out build hashes, Next's own payload and React's empty `<!-- -->` text separators (they move when copy goes into messages), and lists what differs.

## Marketing in every language (P2, as built)

**Publishing.** All five locales are enabled; each page is published per locale. `PAGE_NAMESPACES` (`src/i18n/pages.ts`) lists every public page (or section, like `/compare`) with the namespaces it reads, besides the header and footer's `common` and `site`. `src/i18n/publish.ts` publishes a page in a locale once all of them are translated (`publishedPages`, `publishedLocales`, `isPublished`). A page calls `requirePublished(path)`, or a section's layout does (`compare`, `ats`, `resume-examples`, `resume-templates`): elsewhere it prerenders as that language's 404, with status 404. A nested `generateStaticParams` must keep listing every page for every locale: one that returns nothing for a locale makes Next prerender none of the route's pages, English included (seen on a production build). Sign-in reads `login`, `account` and `signIn` and is published in every language since the leftover sweep; the page passes the form's words (and its legal links in the page's language) as props. The guides are published since P5 (below).

**Links.** `getLocalize()` (or `localizer(locale, published)`) maps a path to the page's own language when that page is published there, and leaves everything else plain: app paths (`/studio`, `/dashboard/…`) are never prefixed, so a translated page never sets the app's language cookie. A translated footer lists only its language's pages; related-link lists drop unpublished pages; inline links to English-only guides stay plain.

**Pages.** Server parts read `getMessages`, `getFormat` and `getLocalize` in the async page and pass `t`, `format` and `href` to synchronous sections (testable with `renderToStaticMarkup`). Client islands get their strings as props from the server, never a provider; `src/components/match-check` takes optional copy with English defaults because the studio uses it too. Prices stay US dollars, formatted per locale (`usd`, `priceCopy`, `creditCopy` in `src/app/[lang]/(marketing)/_components/price-copy.ts`, whose English matches `src/lib/billing/prices.ts` and `src/config/topup.ts` word for word); English lists keep the house style (no serial comma) and other languages use `Intl.ListFormat` (`joinList`). Counts come from the same code in every language (`countClaimWith`). `llms.txt` and `llms-full.txt` are built from the English messages.

**SEO.** `localizedMetadata()` gives each page its own canonical, `alternates.languages` for every locale it is published in plus `x-default` (English), and Open Graph `locale`/`alternateLocale`; a page in English only gets no alternates. The sitemap lists English pages first, then each translated page, every entry with the same alternates (IndexNow still reads `<loc>`). JSON-LD says `inLanguage` on translated pages; English JSON-LD is unchanged.

**Language picker and hint.** The footer links the same page in each language it is published in (`src/components/site/language-picker.tsx`, full page loads; it reads the path without its prefix, so the server's `/en/…` and the browser's `/…` agree). On English pages only, `language-hint.tsx` offers the page in the browser's first language when it's published there: fixed at the bottom (no layout shift), dismissed for good in localStorage (wrapped in try/catch), nothing on the server. No Accept-Language redirects.

**404.** `src/app/[lang]/not-found.tsx` is localized (a gated page, an unknown slug). A URL no route matches still gets the English `global-not-found` (it can't know the language without turning dynamic).

**Legal pages** are translated in full and say the English version applies if the two differ.

**Namespaces.** `signIn` (the sign-in form, dialog, terms line, Otto's sign-in reasons and the signed-out note), `upgrade` (the upgrade and add-credit dialogs, plan cards, billing note and trial notices), `otto` (Otto's limit, plan, error and writing-allowance lines), `shareLinks` (the share dialog, link list, invite prompt), `ui` (dialog close, the optional mark, file drops and checks, voice typing, feedback, the bell), `formats` (the formats gallery and each format's notes), `calendar` (the feed card) and `github` (adding projects from GitHub). `common` adds the referral toasts and the toast region's words, which the root layout passes to `ReferralTracker` and `Toaster`, since no provider reaches that high.

## SEO long tail (P5, as built)

**What's published.** The comparisons (9), the ATS hub and its 13 guides, the resume examples hub and its 24 examples, and the templates page are live in es, pt-BR, fr and de. Each section publishes on its own: `PAGE_NAMESPACES` gives it `product`, `seo` (words the sections share) and its own namespace (`compare`, `ats`, `resumeExamples` plus `lint`, `resumeTemplates`). The page words are messages; the facts and examples are content.

**Content modules** (`src/lib/seo-pages/locales/<locale>/`): `compare.ts` (a function of `CompareValues`: Otto's prices and counts, `usd()`, `date()` and `plural()` already in the language), `ats.ts` (each system's introduction and notes, the general advice, a card's screening tip) and `examples/<slug>.ts` (one per role). The English data is written `as const` (`roles/*.ts`, the competitors in `compare.ts`, the notes in `src/lib/ats/systems.ts`), so `Words<T, Fixed>` (`src/lib/seo-pages/words.ts`) types each translation as the English shape, item for item, without the keys that never change (slugs, names of people, employers and schools, contacts, dates, URLs; the comparison's summary, strengths and picks, which only `llms-full.txt` reads). `withWords()` puts the words into the English objects, so pages draw one `Competitor`, `AtsGuide` or `RoleExample` type in every language. `src/lib/seo-pages/locales/index.ts` (`competitorsIn`, `atsTranslation`) and `locales/examples.ts` (`examplesIn`, also used in the browser by "Start from this example") load one language at a time; their `Record` of every locale makes tsc require all of it.

**Resume examples.** The people, places, employers and US context stay; the text is translated, job titles follow the person's gender, US degree abbreviations stay. A translated example's resume carries `lang`, so its headings come from `sectionHeading` and the studio opens it in that language; `resumeDate()` writes its months and "Present" the language's way (`Abr. 2024 – Actualidad`). The page's "Skills hiring software looks for" stay as US job posts write them, since the match check reads English posts; the page says so. Every bullet and strong line passes the line check of its language and every weak line is flagged by it, and the note under each weak line is `issueText()` from that language's pack (`guides-locales.test.tsx`).

**Comparisons.** Each claim is translated as written, with no claim added or made stronger; prices stay US dollars through `v.usd()`, and dates and numbers are written per locale (`calendarDateIn`, `calendarMonthIn`). Titles and descriptions come from the namespaces; `seo-copy.test.ts` keeps the English ones equal to `src/lib/seo-pages/pages.ts`.

**SEO.** Each guide page has `generateMetadata` through `localizedMetadata()` (self-canonical, every published language plus `x-default`); JSON-LD articles, item lists, breadcrumbs and FAQs say `inLanguage` outside English and keep ISO dates. The sitemap lists each guide in all five languages (`seo.test.ts` counts them); English URLs, titles and descriptions are unchanged. Every dynamic guide route still lists all its slugs for every language in `generateStaticParams`.

**Also translated in P5:** the home and pricing mascot's default title (`common.otto`), the home clips' Play and Pause (`common.video`, through `GuideVideo`'s `labels`), the templates page's preview dialog, image alt and buttons (optional props on `FormatPreviewDialog`, `FormatImage` and `Dialog`, English by default), and the job link check on each guide.

## Content language (P1, as built)

**Detector** (`src/lib/i18n/detect.ts`): function words, resume vocabulary, word endings and accents scored for en, es, pt, fr and de. `detectLanguage(text)` gives `{ lang, confidence }`, `"unknown"` when unsure; `languageOf(text, fallback)` falls back. All-caps words ("MIT", "LA") don't count, so English resumes with foreign names stay English.

**Resume `lang`** (`src/lib/resume/lang.ts`): optional in the resume JSON (`en es pt fr de`). `resumeLang(resume)` reads it, else detects from the person's own words, else English. Imports (file, JSON Resume, LinkedIn) and drafts store a detected language other than English, so English resumes keep their shape. `setResumeLang(resume, lang | null)` is for the language control (null goes back to detecting).

**Lint** (`src/lib/lint/lang/`): one `LintLanguage` pack per language; `CHECK_LANGS` says which languages each check runs for. Length, numbers, repeats and full stops run for every language; `tense` and `passive` are English-only; word checks need the pack's lists. Noun-style lines ("Gestión de…", "Leitung von…") aren't weak. French elisions are their own tokens. Issues carry a non-enumerable `messageId` and `params`; `issueText(issue, messages, locale)` rebuilds the message from the `lint` namespace, and a test keeps the English namespace identical to `message`.

**Import parser** (`src/lib/resume/sections-lang.ts`, `date-words.ts`): headings, month names, present words ("actualidad", "atual", "aujourd'hui", "heute") and range words ("a", "até", "au", "bis") for all four languages. English matches first; "out", "set" and "ago" count as months only before "/" or ".".

**AI.** System prompts stay English and byte-stable; their plain-English line also reads a `<languages resume ui post/>` tag that opens the user message, left out when everything is English. Resume lines and summaries follow the resume's language, notes and questions the app's (`otto_lang`, live locales only), letters, messages and interview questions the post's (detected, else the resume's); interview stories stay in the resume's language so the honesty checks can compare them. Guards add each language's stock phrases, unbacked phrases, blank words, number words and pronouns; outside English the number guard reads "99,9 %", "12 000" and "1.250,5". The moderation pre-check has word lists for all four languages. Speech to text takes an optional `language` form field.

**PDF and Word.** Default headings, extras titles, the document title and its language tag (`<Document language>`, `w:lang`) follow the resume's language; the person's own headings win. A letter's date and title follow the letter's language.

## Emails (P4, as built)

**Language.** Every email and bell note follows `user_settings.locale`, read where it is written: the crons (trial reminders, follow-ups and interviews, career check-ins, weekly matches, portfolio views), a share link's first view, the processor-notice script and the unsubscribe page. Null, or a value we don't have, is English (`emailLocale` in `src/lib/notifications/locale.ts`). The words are the `emails` namespace, read straight from each locale's file (`emailMessages(locale)`), since crons and scripts have no page; dates, times, counts and prices go through `formatFor(locale)` (prices stay USD: "US$ 278 por ano").

**Builders.** `trialEndingEmail`, `trialEndingNotice`, `checkinEmail`, `checkinNotice`, `processorNoticeEmail` and `unsubscribePage` take a `locale` (in their input, or last); so do the bell notes `followUpNotices`, `interviewSoonNotice`, `shareViewNotice`, `portfolioViewsNotice` and `matchesNotice`. Subjects, buttons, sign-off, footers and unsubscribe text are all messages. `src/lib/notifications/english-golden.test.ts` renders all of them in English against `golden/english.json`, saved from the code before this change, and checks that no English sentence is left in the other four.

**Links.** `localizedPath(locale, path)` prefixes `/{segment}` only for a live locale other than English: on an app path the proxy sets `otto_lang` and drops the prefix, on a public page it serves that language. A locale that isn't live would stay unprefixed; all five are live since P2. Unsubscribe and one-click links are API paths and never change. The unsubscribe page reads the account's language only after the signed token checks out (a bad link is answered in English), and the RFC 8058 one-click answer stays English JSON.

**Bell notes** are stored as text, in the account's language when they are written; old rows stay as they are and don't change with the language. Storing a kind and its values instead would need the bell (`src/components/notifications`) to render them; not done. Still English: the weekly recap (`src/lib/recap`) and the interview-day and after-interview notes (`src/lib/interviews/autopilot.ts`).

**Sign-in code email.** Supabase renders its auth emails with Go templates and fills `.Data` from the account's `user_metadata`; its docs show branching on it (`{{ if eq .Data.Domain "…" }}`). So `src/lib/auth/code-email.ts` builds one subject and one body with a block per language, `{{ if eq (printf "%v" .Data.otto_locale) "es" }}…{{ else }}English{{ end }}` for the body (`printf` keeps a missing key from reaching `eq` as nil). Supabase caps a subject at 255 characters, so the subject reads the language once (`{{$l:=print .Data.otto_locale}}`) and shares its ": {{ .Token }}" ending (`compactSubject()`; a test keeps it within 255). English renders byte-identical to the old template. The key is `otto_locale`, not `locale`, because Google sign-in can write a `locale` of its own. It is set:

- at sign-up: `POST /api/auth/request-code` takes an optional `locale` (the sign-in page's language), else the `otto_lang` cookie, live locales only, and passes it as `options.data`, which Supabase stores only when it creates the account. English sends exactly what it always did. The login page doesn't send `locale` yet.
- on a change: `PUT /api/language` saves the language as before, then calls the admin API (`updateUserById`, which merges the key into the metadata). If that fails, the language is still saved and the request still succeeds.

**Live since 2026-11-25:** both templates (Confirm sign up, Magic link) were pasted in the Supabase dashboard (Authentication → Emails), with no access token created. To change them again, paste from `CODE_EMAIL`, or run `SUPABASE_ACCESS_TOKEN=… bun scripts/email-templates.ts` (shows what is saved) and then with `--apply`. Accounts that chose a language before this have no `otto_locale` until they change it again.

If Supabase ever drops template branching, the fallback is a Send Email Hook: an HTTPS hook (`hook_send_email_uri`, signed with a standard-webhooks secret) that receives the user and the code and sends the email itself through Resend, in the account's language.

## Jobs (P6, as built)

**Post language.** `normalizeJob` reads each post's language from its title and own text (`postLanguage`, the P1 detector on the first 4,000 characters) and keeps it in bits 9-11 of `listings.flags` (`codes.ts`: 0 not known, 1 en, 2 es, 3 pt, 4 fr, 5 de), so the table grows by nothing. Only rows a read adds or rewrites get it; `NORMALIZE_VERSION` is unchanged, so older rows stay 0 and read as English. Personio is still fetched with `?language=en` (its feed has no per-post language).

**Job languages.** `user_settings.job_langs` (null until chosen; a check allows one to five of `en es pt fr de`) is saved with Looking for (`langs` in the choice, null goes back to the default). `jobLangsFor` (`job-langs.ts`) turns it into the languages a list keeps: the saved ones, else, once `JOB_LANGUAGES_LIVE` is on, the app's language and English; null keeps every language. The match index query keeps posts whose language code is in the list (English also keeps code 0), and so do an opening's copies. The control is a fourth menu on the Looking for line, hidden behind `JOB_LANGUAGES_LIVE` like the language setting; while it is off, lists keep every language, so English lists don't change.

**Titles.** `occupations/translate.ts` reads a title in Spanish, Portuguese, French or German as English words ("Analista de Dados Sênior" is "senior data analyst", "Softwareentwicklerin" is "software developer", "Chef de projet" is "project manager") from per-language tables in `occupations/langs/`: job words, qualifiers, level words ("Pleno", "Semi Senior" drop; "Sênior", "Júnior" move to the front), joins ("de", "für") and German compounds. The job word goes last, qualifiers before it in English order, training words ("Stagiaire", "Werkstudent") after it. `readTitle`, `roleFamily` and `seniorityOf` read the English words first, so the role gate, the rules fallback, the rebuild (which re-reads every stored title) and the occupation search all understand them. A title is read as another language only when it has a word of that language, or a "de" joining a job to a known word; words English spells the same way ("Stage", "Client", "Commercial", "Remote") are marked `~` and only count in a title that is already foreign. A test keeps all 52,618 English occupation names and aliases unchanged.

**Years and levels.** `minYearsOf` also reads "5+ años de experiencia", "3 anos de experiência", "5 ans d'expérience", "mindestens 5 Jahre Berufserfahrung" and the reverse order ("experiencia mínima de 3 años", "Erfahrung von mindestens 3 Jahren"), so `LEVEL_MAX_YEARS` hides those posts from entry-level lists too.

**Hiring emails.** The tracking classifier (`src/lib/inbound/parse/classify-langs.ts`) has applied, interview, assessment, rejection and offer phrases, the "if you're shortlisted…" filter and job-alert words in all four languages; `extract.ts` reads their subject lines and "Puesto:", "Vaga:", "Poste :", "Stelle:" labels. The Worker doesn't classify, so it is unchanged.

**Words.** `matchReasons` (match reasons, notes, visa lines; written on the server in the reader's `otto_lang` language, with the locale in the day's match cache key when it isn't English) and `jobsShared` (Looking for, the occupation search, Mark as applied; components outside the dashboard take them as props with English defaults). The occupation search's group names are translated in the browser from the occupation's code, since the search answer is cached for everyone.

## Guardrails

- `tsc` checks every locale has every key; a vitest suite checks placeholder and tag parity, plural categories, no empty or untranslated strings.
- `otto/no-literal-copy` (`eslint.config.mjs`): JSX text and the `aria-label`, `title`, `placeholder` and `alt` props in `src/**/*.tsx` must come from the messages or a prop. Names, marks and example values are allowed by exact text (`COPY_ALLOW`); single letters and `<style>`/`<script>` are code. Files not checked are listed with their reason in `COPY_ELSEWHERE`, including the areas still in English below.
- Golden English HTML: prerendered pages must be byte-identical before and after each extraction step.
- `next build` must keep marketing routes static or ISR.
- `otto/no-en-us-intl` bans a literal `"en-US"` passed to `Intl.*` or `toLocale*`/`localeCompare` outside `EN_US_ALLOWED`: English sources and defaults, machine text (time-zone math, analytics, AI input), the API routes and the areas other phases own.
